ウィンドウ跨ぎのタブ検索 推奨

今検索は描画済み DOM を隠すだけで、Chrome に一切問い合わせない。描画元のモデルが tabs.query({ windowId }) に閉じているので、他のウィンドウは原理的に見えない。実装漏れではなく設計の境界。

作る検索語がある間だけリスト下に「他のウィンドウ」節を出す。クリックでそのウィンドウを前に出してタブを開く。

  • 他ウィンドウのタブをモデルに混ぜない。D&D・キーボード・差分描画のすべてが「モデル＝現ウィンドウ」に依存している。独立した節として描くのが安全。
  • 初版はファビコンとタイトルだけにする。検索結果までサムネを撮るとキャプチャ列が伸びる。

サイトごとの自動グループ化 推奨

今グループの表示と手動操作は揃っている。tabs.group / ungroup は D&D とキーボードから既に使われる。足りないのは「まとめて切る」入口だけ。

作るツール列にひとつ追加。ホスト名で束ね、2 つ以上あるホストをグループにする。名前はホスト名、色はハッシュ。取り消しを必ず添える。

  • グループ化すると Chrome がタブを隣接位置へ動かす＝ index が変わる。直後に再同期を呼ばないと並びがずれる。
  • 1 ホスト 1 グループはホストが多いと逆に読みにくい。しきい値を設定にするか決め打ちにするかは要判断。

タブのロック（閉じない） 推奨

今パネルからの close はほぼ ops.remove に集約されている。例外がひとつ、重複検出ツールだけ chrome.tabs.remove を直接呼んでいて経路の外にある。

作るタブに鍵を付け、パネル内のあらゆる close 経路がそれを見る。前提として上の例外を先に揃える。

  • 拡張は tabs.onRemoved を拒否できない。タブバーの × や Ctrl+W は止められないので、これは「このパネルからの誤爆を防ぐ」機能であって、タブの保護ではない。UI にそう書く必要がある。
  • ops.remove は失敗時に自前でトーストを出す。素直に繋ぐとツール側のトーストと二重に出る。

検討して落とした案

案落とした理由
タブ別のメモリ表示安定した API が無い。chrome.processes の可用性は未実測で、使うなら実測が先になる。
リーディングリスト連携Chrome 自身の UI と重複する。同じものを二か所に置くことになる。
古いタブの自動クローズ取り返しがつかない。放置タブツールの休止（hibernate）で目的は足りている。

どれを選んでも守ること

選定後の実装に効く制約

  • ネットワークを使う機能は足さない。README の「一切通信しない」と、それを検証しているテストの両方が崩れる。天気と予定のウィジェットを消したのはこのため。
  • 新しい権限を要求しない。5 案はいずれも現行の権限で足りる。
  • タブ列の幾何を測る新しいテストは widgets: [] を明示する。ツール列が既定オンで 184px 取るため。
  • 文言は英語と日本語の両方に入れる。片方だけだとユニットテストが落ちる。
見積の単位は「新規＋変更の行数」で、テストコードは含まない。既存モジュールのコメント込みの密度に合わせた実績ベース。
